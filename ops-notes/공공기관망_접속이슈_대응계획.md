# YPP 공공기관망 접속 이슈 정리

## 1) 현재 상황
- YPP 웹사이트는 여러 페이지에서 Google Apps Script를 통해 데이터를 조회/저장하고 있습니다.
- 전력거래소, 남부발전 등 공공기관 접속 환경에서 일부 페이지가 "데이터를 불러오지 못함" 증상을 보이고 있습니다.
- 페이지 자체는 열리지만 목록/데이터 API 호출이 실패하는 케이스가 확인되었습니다.

## 2) 원인 판단
단일 원인으로 확정할 수는 없지만, 아래 가능성이 큽니다.
- 기관망 보안정책으로 Google 관련 도메인 호출 제한
- 보안 프록시/SSL 검사 장비 간섭
- CORS/Preflight(OPTIONS) 차단
- 리다이렉트/쿠키 정책 충돌

핵심 판단:
- 사이트 코드 문법 문제라기보다, "공공기관망 정책 + 브라우저의 Google 직접 호출 구조" 영향일 가능성이 높습니다.

## 3) 현재 구조의 한계
현재 구조(리스크 큼):
- 사용자 브라우저 -> Google Apps Script 직접 호출

공공기관 환경에서는 이 직접 호출이 차단될 수 있어, 사용자가 데이터 미노출 문제를 겪습니다.

## 4) 대응 전략
### 4-1. 단기 대응 (즉시)
- 기관 IT 담당에 `script.google.com` 등 관련 도메인 허용 여부 확인 요청
- 프론트엔드 실패 처리 강화 (명확한 오류 안내 + 재시도 + 대체 안내)
- 접수 기능 장애 시 이메일/전화 등 대체 채널 병행

### 4-2. 중기 대응 (구조 개선)
- 브라우저의 Google 직접 호출을 줄이고 우회 구조 도입

권장 구조:
- 사용자 브라우저 -> 중간 API(서버리스) -> Google Apps Script -> Google Sheet

효과:
- 공공기관망에서 Google 직접 접근 차단 영향을 줄일 수 있음
- 서비스 안정성 향상

### 4-3. 조회형 데이터 페이지
- 뉴스/갤러리/일반 목록은 정적 JSON 캐시 병행 가능
- GitHub Actions로 JSON 자동 갱신 배포 가능
- 장점: Google 런타임 호출 감소

### 4-4. 신청/신청확인 기능 (아카데미)
이 영역은 실시간 입력/조회가 필요하므로 단순 JSON 캐시로 대체 불가합니다.
- 신청: 데이터 쓰기 필요
- 신청확인: 실시간 조회 필요

따라서 이 기능은 중간 API(서버리스) 방식이 사실상 필수입니다.

## 5) GitHub Pages 환경에서 가능한지
가능합니다. 전통 서버가 없어도 구현 가능합니다.

가능한 선택지:
- Cloudflare Workers
- Vercel Functions
- Netlify Functions

권장:
- Cloudflare Workers 무료 플랜으로 신청/신청확인 API부터 우선 전환

## 6) 무료 구현 가능 여부
- 무료로 시작 가능
- 다만 트래픽이 크게 증가하면 유료 전환 검토 필요
- 기관망 정책이 매우 강하면 Cloudflare 도메인도 차단 가능성은 있어, 기관별 검증 필요

## 7) 실행 우선순위
1. 단기 운영 안정화
- 오류 안내 문구 정비
- 대체 접수 채널 공지
- 기관망 에러 로그 수집

2. 핵심 기능 우선 전환
- 아카데미 교육 신청/신청확인부터 서버리스 API로 분리

3. 조회형 페이지 전환
- 순차적으로 JSON 캐시 구조 도입

4. 기관 IT 협조 병행
- 도메인 허용/정책 확인 요청

## 8) 클라이언트 전달용 문안(초안)
전력거래소나 남부발전 같은 공공기관 환경에서는 기관망 정책에 의해 외부(Google) 호출이 차단되어 데이터 조회가 실패할 가능성이 큽니다.
현재 사이트 일부 기능이 Google Apps Script 직접 호출 구조로 되어 있어 접속 환경 영향을 크게 받는 상태이며,
단기적으로는 기관 IT 정책 확인 및 장애 안내/대체 접수 채널을 병행하고,
중기적으로는 GitHub Pages 환경에 맞는 서버리스 중계 API 방식으로 전환하여 공공기관 접속 안정성을 개선하겠습니다.

## 9) 결론
- 원인: 공공기관망 정책 영향 가능성 높음
- 단기: 안내 강화 + 기관 협조 + 대체 채널
- 중기: 신청/신청확인 API 우선 우회
- 장기: 조회형 데이터까지 점진적 구조 개선

| P0 | 입력형 | 아카데미 신청확인 조회/수정 | `pages/academy/index.html` | 실시간 조회/수정, 민원 가능성 높음 |

- 따라서 1차 전환 범위는 P0(입력형), 2차는 P1, 3차는 P2 순으로 권장합니다.

## 11) 아카데미 서버리스 전환 시 실제 수정 대상 파일 (확정)

### 11-1. 프론트엔드 (필수)
1. `pages/academy/form.js`
- `WEBAPP_URL` 직접 호출 제거
- 중계 API 엔드포인트로 교체
	- `POST /api/academy/apply`
- 타임아웃/재시도/오류 메시지 표준화

2. `pages/academy/index.html`
- 신청확인 검색 로직의 직접 Apps Script 호출 제거
- 수정 저장 로직의 직접 Apps Script 호출 제거
- 중계 API로 교체
	- `POST /api/academy/check`
	- `POST /api/academy/update` (수정 기능 유지 시)

3. `pages/academy/courseData.js`
- Apps Script fallback 하드코딩 제거 또는 비활성화
- 조회 API를 중계 API/캐시 JSON 경로로 전환

4. `pages/academy/psac-overview.js`
- 직접 Apps Script URL 제거
- 중계 API/캐시 경로 사용으로 전환

5. `js/config.js`
- Academy 관련 URL 설정을 중계 API 기준으로 정리
- 직접 `script.google.com` 주소 의존 최소화

### 11-2. 서버리스 API (신규)
1. `POST /api/academy/apply`
- 요청 검증 -> Apps Script 전달 -> 표준 응답 반환

2. `POST /api/academy/check`
- 요청 검증 -> 조회 결과 반환

3. `POST /api/academy/update` (선택)
- 신청확인 이후 수정 기능 지원 시 필요

### 11-3. Apps Script (연계 변경)
- 액션별 파라미터 명세 표준화 (`apply`, `check`, `update`)
- 토큰 검증(가능 시) 및 응답 스키마 통일

## 12) 권장 전개 순서 (1차 구현 범위)
1. 아카데미 입력형(P0) 전환
- `form.js`, `index.html`의 신청/확인/수정 경로를 우선 교체

2. 아카데미 조회형(P1 일부) 정리
- `courseData.js`, `psac-overview.js`를 중계 API 또는 캐시로 전환

3. 공통 설정 정리
- `js/config.js`에서 직접 Google URL 의존 제거

4. 이후 비아카데미 조회형(P1/P2) 순차 전환
